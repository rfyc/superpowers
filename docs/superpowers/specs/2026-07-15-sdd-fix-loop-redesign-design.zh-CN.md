# SDD 修复循环重新设计——设计规范

**状态：** 已批准的设计（2026-07-15 与 Jesse 头脑风暴）；实现计划随后给出。
**目标：** 使 subagent-driven-development 技能的审查-修复循环收敛且自主，并让文档可读，而不改写其经 eval 调优的语言。
**硬性不变量：** 现有经 eval 调优的句子可以移动；但不会被改写。新机制随 drill 证据一起发布。

## 问题

四个问题，全部在真实会话中观察到：

1. **病态审查循环。** 循环字面上就是"重复直到批准"——没有轮次上限。每次重新审查都是对整份 diff 的一次全新完整审查，因此一个不确定的前沿审查者每轮都会浮出新的发现，而不是验证修复。结果：实现、审查、修复、审查、审查、修复、审查、修复——没有任何断路器。严格成本规范（2026-06-10）独立地把审查循环次数测为最大的运行间成本差异来源。
2. **自相矛盾的修复策略。** 流程图和"Constructing Reviewer Prompts"派发专门的修复 subagent；Red Flags 说"Implementer（同一 subagent）修复它们"；implementer-prompt.md 的"After Review Findings"部分假设 implementer 将被重新参与。一个技能里对"谁修复？"有三个答案。
3. **堆砌的结构。** 十三个顶层部分；针对某一活动的指导分散在其中四个部分。"Constructing Reviewer Prompts"是一个大杂烩，装着审查者指导、修复策略、最终审查策略和计划冲突裁决。
4. **Red Flags 格式。** 七个兄弟技能使用 `| Excuse | Reality |` 合理化表格；SDD 却带着一个 17 条要点的"Never"列表，外加三个"If X"小模块。

## 设计决策

| # | 决策 | 理由 |
|---|----------|-----------|
| 1 | 最初的 implementer 修复自己的审查发现——在原地恢复它。 | 它已经持有任务上下文；所有权胜过路过式打补丁。新的"修复 subagent"要为每条发现重建上下文，且缺乏任务框架。 |
| 2 | 重新审查限定在发现的范围内。 | 每轮的全新完整审查是空转的引擎。限定范围的重新审查使循环在结构上收敛；最终的整分支审查仍是广泛的兜底。 |
| 3 | 断路器设为五个修复轮次：三次恢复，然后在一个更有能力的模型上做两次全新派发。 | Jesse 的决定。一个扛过三次恢复的循环通常意味着 implementer 看不到自己的问题——全新的有能派发一举解除锚定并提升能力。 |
| 4 | 触发时，控制器裁决并路由。没有新的人工检查点——结构性失败到达现有的 BLOCKED 停止。 | SDD 的意义在于自主执行。控制器持有审查者所缺乏的计划和跨任务上下文；现有文本已批准它（"在审查循环中裁决它"），却从未规定机制。 |
| 5 | 按生命周期重组 SKILL.md，保留调优过的句子。 | 从根源上修复"难以跟读"。内容移到其使用点，契合项目方向（最近的提交把 recap 部分折叠进使用点）。 |
| 6 | 把 Red Flags 转换为 `| Excuse | Reality |` 合理化表格；把硬性规则移到其使用点。 | 与其他七个技能一致。借口得到反驳；规则在读者行动处得到执行。 |

## 修复循环

触发条件：任务审查返回规范 ❌ 或任何 Critical/Important 发现。

**第 1–3 轮——恢复最初的 implementer。** 逐字发送发现（Critical/Important 加规范缺口）。implementer 修复、重新运行覆盖测试、把修复报告追加到其现有报告文件，并返回简短契约。在没有 agent 恢复能力的 harness 上，"恢复"是一次携带 brief、报告文件和发现的全新派发——无论哪种方式，报告文件都是持久记忆。

**第 4–5 轮——新的 implementer，更有能力的模型。** 完整任务上下文：brief、报告文件、未解决的发现，以及框架"先前的 implementer 尝试了 N 次；现在任务归你。"

**每轮重新审查都是限定范围的。** 重新审查者收到 brief、更新后的报告、原始发现列表，以及一个修复限定的 diff 包（`review-package FIX_BASE HEAD`，其中 FIX_BASE 是审查者上次审查过的 head；脚本已经接受任意范围）。它逐条判定每条发现已解决/未解决，并只标记修复 diff 中的新破坏。修复未触碰的代码上的新发现被报告为非阻塞；控制器将其记入 ledger 供最终审查使用。

**修复报告完整性门（现有规则，保留）：** 在派发重新审查之前，确认修复报告写明了覆盖测试、运行的命令和输出。

**无提前退出。** 控制器在达到上限之前从不裁决——提前退出会重新打开当前内容刻意关闭的"预判发现以省掉一次审查循环"漏洞。有一个例外，与今天相同：与计划文本所规定的内容相冲突的发现会立即交给人类（计划权威，而非循环空转）。

**Minor 发现** 永不进入循环：到达时记入 ledger（现有规则，保留）。

### 触发时的裁决

在第五轮失败后，控制器停止派发，并依据 brief、计划和跨任务上下文逐条判断每个未解决的发现：

- **有争议或错误** → 记入 ledger 并附一行裁决（"controller: reviewer wrong because X"），继续。最终审查会看到双方。
- **真实但不承重** → 记为已知未解决，继续。之后触及该区域的派发会携带对该条目的引用。
- **真实且承重**（后续任务建立在其上，或它揭示了一个计划缺陷）→ 现有的 BLOCKED 停止。搁置继续会把结构性失败推迟到最昂贵的时点，并让依赖方在其上构建，因此结构性失败会停止运行——通过已经存在的停止条件，而非新检查点。

每条裁决都是一条 ledger 条目。静默丢弃仍然被禁止。

## 文档重构

新骨架，按执行顺序：

1. 引言——为什么用 subagent、核心原则、叙述、持续执行
2. When to Use——不变，包括决策图
3. The Process——为新的循环更新流程图
4. Setup——worktree、ledger 检查/恢复、飞行前计划审查、todos
5. Model Selection——仍是单一横切部分；每次派发都咨询它，因此把它折叠进使用点会重复五次
6. The Task Loop——五个编号步骤：
   1. 派发 implementer（task-brief 脚本、五部分派发构成、模型行必填）
   2. 处理报告（DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED）
   3. 审查任务（review-package 脚本、审查者派发构成、约束透镜、不预判、⚠️ 处理）
   4. 修复循环（上面的机制）
   5. 完成任务（ledger 追加、todo 更新）
7. Final Review——包、模型固定、一次修复波、一次限定范围的重新审查、裁决
8. Finish——finishing-a-development-branch
9. Common Rationalizations——表格
10. Example Workflow——更新以展示一轮基于恢复的修复轮，且断路器未触发

"Constructing Reviewer Prompts"、"File Handoffs"和"Durable Progress"各自溶解到适用规则的步骤中。每条经 eval 调优的句子都恰好落在一个新位置；实现计划中的移动映射表追踪源 → 目标，以便审查可以验证没有内容被丢弃或改写。

## 合理化表格

借口形状的 Never 条目转换为行；新行覆盖循环病理。草稿行（最终措辞在实现时给出）：

| 借口 | 现实 |
|--------|---------|
| "规范符合性差不多就行" | 审查者发现缺口 = 没完成。 |
| "我自己修就行，派发是开销" | 控制器修复污染你的上下文并跳过审查。恢复 implementer。 |
| "再来一轮就会收敛" | 越过上限，轮次不会收敛。裁决。 |
| "反正审查者总会发现新的东西" | 限定范围的重新审查检查修复，而非口味。未触碰代码上的新发现进入 ledger，而非循环。 |
| "这个发现显然错了，我把它丢掉" | 你只在达到上限时裁决，且每条裁决都是一条 ledger 条目。静默丢弃被禁止。 |
| "修复很小，跳过重新审查" | 未审查的修复正是回归落地的方式。 |

不是借口的硬性规则（绝不并行 implementer、绝不在没有 diff 文件的情况下派发审查者、模型行必填、绝不重新派发已 ledger 完成的任务）移到其使用点。

## 提示词模板

- **implementer-prompt.md**——"After Review Findings"为恢复语义重写：你将被带发现恢复；修复、重新运行覆盖测试、追加到你的报告文件、返回简短契约。
- **task-reviewer-prompt.md**——仅限初始审查；末尾的重新审查句移出。
- **re-review-prompt.md（新增）**——限定范围的重新审查契约：输入是 brief、更新后的报告、原始发现、修复限定的 diff 包；输出是逐条发现的判定（已解决 / 未解决）、修复 diff 中的新破坏，以及其外的非阻塞观察。用独立模板，因为这是不同的契约——重载完整审查模板造成了当前的歧义。
- **接管派发（第 4–5 轮）**——由 implementer-prompt.md 加 SKILL.md 指导（brief、报告路径、未解决的发现、接管框架）构成；无新模板文件。

## 最终审查循环

不变：merge-base 包、最有能力的模型、一个持有完整发现列表的修复者。新增：对修复波恰好一次限定范围的重新审查，然后控制器裁决。残余的承重发现会在 finishing-a-development-branch 处浮出，而人类已经在那里了。分支的收尾也得到一个有界循环。

## Evals

`evals/` 中三个新的 drill 场景：

1. **恢复，而非重新派发：** 任务审查返回发现；控制器必须恢复同一个 implementer，而不是派发修复 subagent。
2. **断路器触发：** 一个种子化的永不满足的审查者；控制器必须在第五轮失败后停止派发、裁决、记 ledger 并继续——而不是循环。
3. **结构性发现停止：** 一个承重的发现（后续任务依赖它）；控制器必须通过 BLOCKED 停止，而不是搁置。

外加对现有 SDD 场景的前后运行，以捕获重组引入的回归。

## 非目标

- Ledger 会话定域——由 PR #1943 负责。本工作触及相同的部分，因此实现计划注明冲突风险。
- 脚本变更——task-brief 和 review-package 已经做了新循环所需的事。
- 对 executing-plans 或 requesting-code-review 的变更，超出最终审查指针继续可解析的范围。
