# SDD 任务作用域审查派发（Task-Scoped Review Dispatch）

让 subagent-driven-development 的每任务审查更便宜、更快，同时不削弱它们，方法是把每任务审查提示词限定在任务范围内并停止冗余工作——而最终分支审查保持广泛。

## 问题

SDD 中每任务的代码质量审查者经常对单任务 diff 做分支审查级别的工作。来自两次真实本地 SDD 会话的证据：`a1a6719a-6109-453a-9933-34ae396f5bae`（sen-core-v2）和 `0cc1a12d-9984-4c35-8615-9d42dadb2c47`（serf），都在 `~/.claude/projects/` 下：

- 在 sen-core-v2 会话中，7/8 个质量审查者在仓库范围内运行了 grep；最贵的一个在约 200 秒内运行了 50+ 条 Bash 命令。跨两个会话，质量审查者的成本是同一任务上规格审查者的 4-8 倍。
- 规格审查者，其提示词包含 "Only read files in this diff. Do not crawl the broader codebase,"，保持克制：6-16 次工具调用，14-65 秒。
- 没有审查者自主运行重型测试。每一次观察到的包级或重复测试运行都是由控制器编写的提示词显式请求的（"check all uses," "run tests if useful, especially race-focused ones," "does anything else read `Meta()`?"）。

根本原因，按影响排序：

1. **每任务质量提示词继承了合并就绪审查。** `code-quality-reviewer-prompt.md` 委托给 `requesting-code-review/code-reviewer.md`，后者询问架构、可扩展性、安全性、生产就绪性，并以 "Ready to merge?" 结束。该框架在单任务 diff 上授权了分支级别的广度。规格提示词的 diff 作用域防护从未被带过来。
2. **控制器在编写审查者提示词上得不到指导**，因此它发明了开放式指令（"check all uses"），审查者会按字面理解。
3. **整个流水线中重复的工作。** 质量模板的"Plan alignment"维度重新检查规格审查者刚验证过的东西。审查者重新运行实现者已经在相同代码上运行过（并附 TDD 证据报告过）的测试套件。
4. **每任务和最终审查共享一个模板**，因此任何地方都没有"每任务窄、最终广"的表述。

一份现场报告（`~/2026-06-09-code-quality-reviewer-scope-budget-issue.md`）最先标记了这一点。它引用的会话和头条数字无法验证，但它的定性诊断在两次真实本地会话上得到确认。对它的一处修正：跨切面审计（锁顺序、变更的契约）有时是*正确*的审查方法——修复必须把广度限定在已陈述的具体风险之后，而不是禁止它。

## 目标

- 每任务审查限定在任务范围内：diff 优先阅读、有理由的扩展、无冗余测试运行。
- 最终整分支审查保持当前广度。
- 审查捕获的东西不减少。

## 非目标 / 明确保留

- **完整复审保留。** 当审查者在修复后重新审查时，它仍以完整阅读广度审查整个任务。（它不会重新运行实现者刚在修订后代码上运行的测试。）这刻意拒绝了现场报告的"复审预算"补救：其最差引用示例（一次运行 `-race` 和 `-count=100` 循环的复审）的成本由下面的测试预算来抑制，而不是通过收窄复审者阅读的内容。
- ~~**两个审查阶段保持分离。** 规格合规性和代码质量仍是独立的 subagent，串行门控。不合并。~~ **被下面的成本迭代取代**：实时 eval 经济学显示每次派发的开销主导成本，维护者把所有东西都摆上了台面。每任务阶段现在是一个任务审查者给出两个裁决；独立的广泛最终审查保留。
- **协调者保留模型判断。** 审查不强制模型层级，任何方向都不。
- **`requesting-code-review/` 不被触碰。** 它仍是最终分支审查和临时审查的广泛模板。
- 裁决顺序（规格合规性在质量之前报告）、修复-再审查循环，以及修复 Critical/Important 发现的要求都不变。

## 成本迭代（发布后 eval 经济学）

一旦质量加固行文（证据规则、约束携带、纯净输出）落地，实时前后运行暴露出成本回归：go-fractals 从 42.8 分钟 / 14.5M tokens（首个任务作用域版本）上升到 69.9 分钟 / 32.2M（加固版），同时达到基线同等的质量（盲评 8.5 vs 8.5）。逐 subagent 轮次分析将成本归因于，按顺序：廉价模型在多步骤工作上多花 2-3 倍的轮次（1197 个 subagent 轮次中有 678 个是 haiku）、每次派发的开销（每任务 3 次 subagent 启动，每次都重新推导 diff；控制器协调占了一半的钱），以及证据规则叙述。

- **迭代 1：** 轮次计数胜过 token 价格的模型指导（多步骤工作使用中档下限）、可选的内联 diff、引用而非叙述的证据、Important = 修复前不可信、只针对 Critical/Important 派发修复。结果：68.2 分钟 / 22.9M——tokens 下降 29%，墙钟持平；当措辞为可选时，控制器在 22 次审查派发中只粘贴了 2 次 diff。
- **迭代 2：** 每任务规格和质量审查合并为一个 `task-reviewer-prompt.md`（一个审查者、一次 diff 阅读、两个裁决；一次修复派发处理两类发现）；实现者在迭代时运行聚焦测试，提交前运行一次完整套件。结果（go-fractals）：47.5 分钟 / 15.7M / $13.55——每个轴都击败基线，盲评 9/10 vs 基线 7/10。
- **迭代 3：** 校准将阻塞合并的可维护性损害（逐字重复、吞掉的错误、无断言的测试）命名为 Important，Minor 发现必须粘贴到最终审查中进行分流；审查者的怀疑扩展到实现者的设计理由（"按 YAGNI 留着"是声称，不是裁决）；diff 作为文件交给审查者（`git diff > /tmp/sdd-task-N.diff`，重定向使其永不进入控制器的上下文；审查者一次 Read 调用），因为粘贴到提示词的指导因本地理性上下文经济的原因未被采纳（11-17 次派发中的 0-6）。
- **最终冻结配置（e355795），全部五个场景通过：** go-fractals 44.4 分钟 / 13.4M / $11.67（对比基线 -32% 时间、-37% tokens、-27% 美元）；svelte-todo 62.8 / 19.7M / $15.76（-21% / -28% / -25%）；rejects-extra-features $1.31（对比 $1.88）；spec-reviewer-flaws 持平；植入缺陷场景（v3：判断调用有开放的透明度门槛，对名字承诺了从未执行的验证的测试有必须修复门槛）通过，缺陷被捕获并修复。

### 迭代 4-5（2026-06-10）：方差诚实、结构性修复、正向配方

相同配置的重跑暴露出运行间方差（相同提示词下 44.4→57.1 分钟；审查者逃生舱胃口在 1.0→6.3 次工具调用/审查之间摆动），因此所有后续声称都使用范围。五个并行实验变体（go-fractals 上）加上真实本地会话的转录挖掘（含负面结果的完整日志：`evals/docs/experiments/2026-06-10-sdd-cost-experiments.md`）产出了最终配置：

- **已采纳：** 最终审查包（最终审查者 33→6 轮，控制器模型价格）；两个模板中 REQUIRED 的 `model:` 行（行文指导曾在会话中途退化一次，为 17 次派发继承了 opus，+$5）；任务简报 + 报告文件（`scripts/task-brief`；保真度锚点，适度节省上下文）；`<git-dir>/sdd/progress.md` 中的进度台账（真实会话在压缩后重新派发了整个已完成的任务序列——约 22 个任务花了 269 次派发）；全包最终修复者（一次真实会话的逐发现修复波比它所有任务的总和还贵）；作用域修复测试；唯一的 SHA 范围碰撞名称（worktree/submodule 安全）；派发组合配方和审查者具名风险预算（微测试：正向配方 3.0 转录值 vs 禁止 4.4 vs 对照 3.6——禁止可能适得其反；见 `2026-06-10-positive-instruction-redesign-design.md`）。
- **已测试并被否决：** 控制器轮次批处理和并行调用流水线（控制器每条消息恰好发出一次工具调用——每次运行中 0 条多工具消息；其 46% 的轮次是思考/叙述，是提示词免疫的底线）；后台派发流水线（机制被采纳 7/28，但收益在这些场景中低于 ±6 分钟噪声底线）。
- **最终验证配置（b81f35b 家族），所有门控通过：** go-fractals 54.1-54.7 分钟 / 14.4-16.6M / $12.81-14.31（基线 64.9 / 21.2M / $16.07）；svelte-todo 55.0 分钟 / 19.3M / $14.99（基线 79.7 / 27.3M / $20.98）；植入缺陷通过 / $2.77。跨全部 8 次同设计 fractals 运行：44.4-57.1 分钟 / 13.4-20.0M / $11.67-14.84——最差的抽取在每个轴上击败基线；典型中段节省约 20-25%。

## 设计

### 共享原则：不要对未更改的代码重新运行测试

实现者的报告包含被审查代码的测试结果和 TDD RED/GREEN 证据。审查者通过阅读来验证。只有当阅读引起现有运行都无法回答的具体疑虑时，审查者才运行测试——而且运行聚焦测试，不是套件。在审查者 subagent 只读的 harness 上（例如 Antigravity 将审查者模板映射到 `research` 类型，该类型无命令访问），审查者改为在其报告中点名它会运行的测试。

修复后，实现者重新运行覆盖修订后代码的测试；复审者不重复那次运行。如今没有东西强制执行该前提：`implementer-prompt.md` 只描述初始的实现-测试-提交流程，没有修复迭代指令。因此本规格还向 `implementer-prompt.md` 添加：修复审查发现后，重新运行覆盖修订后代码的测试，并将结果包含在修复报告中。

此原则出现在两个审查者提示词、实现者提示词和控制器指导中。

### 1. 新文件：`skills/subagent-driven-development/code-quality-reviewer-prompt.md` 变为自包含

停止委托给 `requesting-code-review/code-reviewer.md`。每任务质量审查者获得其自己的作用域提示词模板：

- **框架：** "You are reviewing one task's implementation for code quality." 任务作用域门控，不是合并审查。
- **规格合规性已定论：** 规格审查已通过；不要重新争论需求或计划对齐。
- **保留的审查维度：** 代码质量（清晰度、重复、错误处理）、测试质量（真实行为，不是 mock）、可维护性，以及现有的 SDD 特定检查（单一职责、独立可测性、来自计划的文件结构、本次变更贡献的文件增长）。丢弃：计划对齐、安全/可扩展性/生产就绪维度、合并裁决。
- **作用域预算：** 从 `git diff BASE..HEAD` 开始；先读变更文件；仅为了评估你能点名的具体风险而检查相邻代码。跨切面变更——锁顺序、变更的函数/API 契约、共享可变状态——是合法的具名风险，证明检查调用点是合理的。不要默认爬行代码库。
- **测试预算：** 上面的共享原则，外加：不运行包级套件、竞态检测器或重复/高计数运行，除非你先点名了一个具体的疑似 flake 或 race。否则，在报告中建议重型验证而不是运行它。实现者报告的测试输出中的警告或噪声是发现——输出应纯净（实现者的自我审查也检查这一点）。
- **证据规则：** 审查者用 file:line 证据回答每个 What-to-Check 项，而不是裸的 yes/no。（在实时 eval 运行显示审查者放过了提示词已指给它们的缺陷之后添加——一个可访问性名称检查和一次临时目录清理检查都得到无证据支持的"yes"回答，而缺陷就坐在被审查的 diff 中。）
- **只读规则**以精简形式保留：不改变工作树、索引、HEAD 或分支状态。当前模板中的 `git worktree add` 操作说明句子**不**带入此文件——diff 作用域的审查永远不需要检出另一个修订（与下面的规格提示词清理理由相同）。
- **裁决：** Strengths / Issues（Critical/Important/Minor）/ "Task quality: Approved | Needs fixes."

### 2. `skills/subagent-driven-development/spec-reviewer-prompt.md` 清理

- 移除 `git worktree add` 操作说明句子。只读规则保留；diff 作用域的规格审查永远不需要检出另一个修订。
- 解决 diff-only 防护与"独立验证一切"之间的张力：规格合规性通过对照需求阅读 diff 来判断。实现者的 TDD 证据覆盖"它能运行"——应用共享测试原则。
- 新的第三裁决通道：无法从 diff 验证的需求（存在于未更改代码中、跨越任务）被报告为显式的"⚠️ Cannot verify from diff — controller should check X"项，而不是要么爬行要么静默通过。流程图的二元通过/失败菱形无法路由它，因此控制器指导（§3）定义处理方式：⚠️ 项不阻塞派发质量审查者，但控制器必须在标记任务完成前亲自解决每个项（它持有计划与跨任务上下文）；控制器确认是真实缺口的项被当作失败的规格审查处理并返回给实现者。
- 用有根据的怀疑替换虚构前提 "The implementer finished suspiciously quickly"：把实现者的报告当作关于代码的未验证声称。同样的不信任，没有编造的事实。

### 3. `skills/subagent-driven-development/SKILL.md` 控制器变更

- **模型选择：** 用判断指导替换 "Architecture, design, and review tasks: use the most capable available model"——按选择实现者模型的方式挑选审查者模型，缩放到 diff 的大小、复杂性和风险。"Task complexity signals" 列表被重新调整范围以明确其要点描述实现任务；审查者模型选择遵循同样的判断，因此窄 diff 审查不会自动映射到"广泛的代码库理解 → 最强大模型"。
- **审查者提示词构建**（Red Flags 附近的新指导）：派发审查者时，不要在没有具体的任务特定理由的情况下写开放式指令（"check all uses," "run race tests if useful"）；不要要求审查者重新运行实现者已在相同代码上运行的测试；不要为审查者预判发现（绝不指示审查者忽略或不标记特定问题——在审查循环中裁决疑似误报）。每任务审查是任务作用域门控——广泛审查只发生一次，在最终整分支审查时。（预判规则在一次实时 eval 运行捕获控制器编造"计划禁止共享辅助程序"声称并指示质量审查者不标记植入的 DRY 违规后添加。）控制器还必须将约束任务的规格/设计全局约束——版本下限、命名和文案规则、平台要求——包含在它们粘贴的需求中：一次实时运行把一个 `go 1.26.1` 模块下限放行到 "Go 1.21+" 设计之上，因为没有审查者见过该约束。而且控制器必须在每次派发上显式指定模型——省略的模型继承会话的（通常最贵的）模型，静默破坏模型选择。
- **处理规格审查者 ⚠️ 项**（新指导，紧邻 Handling Implementer Status）：控制器在标记任务完成前亲自解决每个"无法从 diff 验证"项；确认的缺口作为失败的规格审查返回给实现者。
- **最终审查明确保持广泛：** 最终整分支审查者派发节点获得指向 `../requesting-code-review/code-reviewer.md` 的显式指针。（如今该模板只能通过每任务质量提示词的委托到达；一旦移除该委托，未被引用的最终审查模板会被孤立。）Integration 部分中 `superpowers:requesting-code-review` 提供"审查者 subagent 的代码审查模板"的说明被更正为仅适用于最终审查。
- **示例工作流：** 示例中的质量审查者行更新为新裁决词汇（"Task quality: Approved"）；最终审查者的 "ready to merge" 行保留。
- 流程图拓扑不变；⚠️ 通道由控制器指导处理，而非新图分支。

## 这不能修复什么（已知，已推迟）

规格审查者对照控制器粘贴的任务文本来判断；它无法捕获控制器从计划提取期间丢弃的需求。那是"控制器提供完整文本"的架构属性，不是提示词问题，且超出本规格范围。

## 验证

- 插件基础设施测试（`tests/`）仍通过。
- 在变更前后运行 SDD 技能行为 evals（`git submodule update --init evals`，然后按 `evals/README.md`）。具体地：`sdd-go-fractals`、`sdd-svelte-todo`、`sdd-rejects-extra-features`（端到端 SDD，含规格审查者的 YAGNI 门控），以及 `spec-reviewer-catches-planted-flaws`。
- 此变更暴露的已知 eval 缺口：没有现有场景在单个 SDD 任务内植入代码质量缺陷并断言每任务质量审查者捕获它，也没有场景衡量逐审查者探索成本（工具调用/grep 计数）。添加一个覆盖第一个缺口的场景（植入的单任务质量缺陷 → 每任务审查者必须在最终审查前标记它）。对于探索成本，跨前后 eval 转录手动比较审查者 subagent 的工具调用计数。
