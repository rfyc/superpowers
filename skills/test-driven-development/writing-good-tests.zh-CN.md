# 编写好的测试

**在以下情况加载此参考：** 编写或修改测试、添加 mock，或为测试添加清理/辅助方法时。

## 概述

测试的存在是为了捕获某种特定的破坏。这里有两个原则支配一切：

```
1. 每个测试都应说出它捕获的破坏
2. 每个测试都应测试真实的东西
```

严格的 TDD 会自然地同时产生这两点：先写、并看着它对真实代码失败的测试，已经证明它确实会失败；只有当真实依赖被证明是慢的或外部的依赖时，测试才配得上一个 mock。

## 原则 1：说出破坏

在写测试体之前，回答：**哪个生产变更应该让这个测试失败——这个变更是一个 bug 还是一个决策？** 一个测试通过捕获错误的分支、缺失的副作用、错误的参数、边界情况或破坏的契约来赢得它的位置。

**独立推导期望值。** 使用字面量和手工核对过的测试数据；带字面量 `want` 值的表驱动测试是首选形态。由被测代码——或其辅助函数——计算出的期望值，无论该代码做什么都会通过：

```typescript
// ❌ 镜像断言：同一个构建器计算两边 —— 永远为真
const expected = buildSearchQuery({ tag: 'urgent' });
expect(buildSearchQuery({ tag: 'urgent' })).toBe(expected);

// ✅ 手工推导的字面量
expect(buildSearchQuery({ tag: 'urgent' })).toBe('tag:"urgent"');
```

**不要做变更探测器。** 如果只有有意的决策能让测试失败——某个常量的取值、消息的确切措辞、私有结构——那么这个测试会在重构时触发，却在 bug 面前沉睡。要测试依赖该决策的行为：不是 `expect(MAX_RETRIES).toBe(5)`，而是"一次失败的调用会被重试 5 次，第 6 次尝试永远不会发生"。

**测试行为，不是文本。** 断言一个脚本、技能或配置恰好包含某一行，只证明了"源代码就是源代码"。针对受控输入运行脚本，断言输出、副作用或退出码。指导 agent 的文档由消费它的 agent 的行为来测试（superpowers:writing-skills）；给人看的文字根本不需要测试。

**测你的代码，不是框架。** 测试你的代码在其边界处做出的契约——你注册的路由、你发出的查询、你产生的负载。上游机制是它的维护者该写的测试（经典例子：断言你的路由器调用了已注册的处理器——那是框架的测试，不是你的）。当上游行为真的让你意外时，写一个狭窄的特征测试，说出那个假设。同样的边界也适用于你的代码内部：构造函数、getter、常量和琐碎的转发，只有当它们做校验、规范化、默认值、推导、强制约束或引发副作用时才配得上测试——否则就断言第一个依赖它们的、对消费者可见的结果。

### 门控函数

```
在写测试体之前：
  说出会让这个测试失败的生产变更。

  说不出来            → 围绕可观察的行为重新设计
  "源代码文本变了"    → 运行产物并断言其效果
  只有有意的决策      → 是变更探测器；测试依赖该决策的行为

  确认期望值不是用被测代码推导的。
  如果它复用了该代码的逻辑或辅助函数：
    把它替换成字面量或手工核对过的测试数据
```

## 原则 2：测试真实的东西

**mock 不配拥有断言。** mock 断言在 mock 存在时通过、在 mock 缺失时失败——它对于组件本身什么也没说。要断言真实组件的行为；如果你检查的正是 mock，那就去掉 mock，或删掉这条断言。

```typescript
// ✅ 真实行为
expect(screen.getByRole('navigation')).toBeInTheDocument();

// ❌ mock 的存在
expect(screen.getByTestId('sidebar-mock')).toBeInTheDocument();
```

**你的人类伙伴的纠正：** "我们是不是在测试一个 mock 的行为？"

**在正确的层级 mock。** 在替换真实方法之前，了解它的每一个副作用；mock 掉慢的或外部的操作，让测试依赖的部分保持真实。拿不准时，先对真实实现跑一次测试，观察实际需要发生什么。

```typescript
// ❌ 这个 mock 吞掉了重复检测要读取的配置写入
vi.mock('ToolCatalog', () => ({
  discoverAndCacheTools: vi.fn().mockResolvedValue(undefined)
}));

// ✅ 只 mock 慢的服务器启动；配置写入保持真实
vi.mock('MCPServerManager');
```

**让替身具体化。** 当参数、调用次数或顺序是契约的一部分时，就断言它们——一个什么都能接受的 fake 验证不了任何东西。为每个分支（成功、错误、畸形输入）准备各自的测试数据或 spy，这样错误的分支无法满足期望。

**完整镜像真实数据。** 按现实中真实存在的完整结构来 mock——所有有文档的字段——而不仅是你的测试读取的那些。部分 mock 会在下游代码读取被省略的字段时静默失败：测试通过，集成却坏了。

**生产类只承载生产方法。** 只有测试需要的清理逻辑放在测试工具里，绝不能作为生产类上的 `destroy()`。问问自己：这个方法是不是只有测试在调用？这个类是否拥有这个资源的生命周期？答案不对 → 放进测试工具。

**优先用真实组件，而非复杂的 mock。** 当 mock 的搭建超过测试逻辑本身、mock 缺少真实组件具有的方法、或 mock 一变测试就崩时，改用带真实组件的集成测试。**你的人类伙伴的问题：** "这里我们需要用 mock 吗？"

### 门控函数

```
在添加 mock 或测试辅助函数之前：
  列出真实方法的副作用；把测试依赖的部分保持为真实——
  在其之下的慢/外部层级才 mock。

  mock 的响应要完整镜像真实结构。

  只有测试会调用的方法放在测试工具里，不放进生产代码。

  正要断言 mock 本身？
    去掉 mock，或删掉这条断言。
```

## 测试随实现一起发布

TDD 循环——失败的测试、最小实现、重构——这就是"完成"的含义。发布行为需要的测试，而且只需要这些：琐碎的代码和给人类看的文字不配拥有测试，而为满足流程而写的测试会带来永久的维护成本。

## 变异检查

在完成之前，在脑中变异生产代码；对每个现实可行的变异，至少应有一个测试失败：

- 错误的常量或参数
- 错误的分支处理器
- 缺失的状态变更或副作用
- 空的或默认的返回值
- 缺少对零、空、nil、未授权或畸形输入的校验

任何变异都没有测试捕获，说明该行为未受保护——或者这个测试是同义反复。

## 快速参考

| 当你…… | 去做 |
|-------------|-----|
| 写任何测试 | 说出它捕获的破坏——一个 bug，而不是一个决策 |
| 构造期望值 | 手工推导；绝不用被测代码 |
| 测试脚本或文档 | 运行它 / 压测它的消费者；绝不 grep 它的文本 |
| 要测依赖 | 测试你的边界契约，而不是他们有文档的机制 |
| 想断言一个被 mock 的元素 | 测试真实组件，或者去掉 mock |
| 正要 mock 一个方法 | 了解它的副作用；mock 掉慢/外部的层级 |
| 构造 mock 响应 | 完整镜像真实结构 |
| 需要只有测试用的清理 | 放进测试工具 |
| 看着 mock 搭建膨胀 | 改用带真实组件的集成测试 |
| 完成一个测试文件 | 运行变异检查 |

## 警告信号

- 搭建与断言共享同一个对象，保证一定相等
- 测试只能通过 panic、崩溃或缺失的选择器来失败
- 测试在有意的变更上失败，却从不在意外损坏上失败
- 期望值隐藏在循环、构建器或辅助函数后面
- 测试 grep 源代码文本，或断言被移除的符号保持被移除
- 即使只剩下框架，这个测试仍然"有意义"
- 测试只是为了覆盖率而存在，不检查任何副作用或结果
- 断言检查的是 `*-mock` 测试 ID，或去掉 mock 就失败
- 某个方法只有测试文件在调用
- mock 搭建占测试的一半以上，或你说不清为什么需要这个 mock
- "只是为了保险起见"而 mock
